# コーディング規約

Rawgenzo のコードを書く人と AI エージェント向けの決まり。[評価基準票](quality-rubric.md) の 10 項目を、書くときに守る形に直したもの。
書き終えてから監査で直すのではなく、書く時点で基準票の 5 点を取ることを目指す。

数字は目安で、超えるときは理由をコメントに書く。

## 1. 構造

- **依存の向き**は次の一方通行に限る。下の層から上の層を参照しない。Package.swift で強制している。
  ```
  RawgenzoApp / rawdev
    → RawgenzoSurface
    → RAWCore、OperationSurface
  ```
  - RAWCore は AppKit も SwiftUI も読み込まない。
  - OperationSurface は Foundation と Darwin だけを使い、RAWCore も読み込まない。
- **1 ファイルは 1 つの話題**にし、目安は 400 行以下とする。
  - 増えたら、型の `extension` を話題ごとのファイルに分ける。例: `RawgenzoSurface/*Tools.swift`
- **テストも同じ**にする。テストの組(XCTestCase)ごとに 1 ファイルとし、ファイル名を組の名前に合わせる。
- **関数は 40 行以下**を目安とする。
  - 道具のハンドラは、次の順に書く。
    1. 引数を確かめる
    2. 全部の写真で計画を立てる
    3. 保存する
    4. 結果を作る
  - 1 つの段が長くなったら、関数に切り出す。

## 2. YAGNI

- いま使う機能だけを書く。将来のための引数・設定項目・汎用化は、2 つ目の使い道が出てから足す。
- `public` は、モジュールの外から実際に使うものにだけ付ける。
- 使われなくなったコード・引数・設定は、その変更の中で消す。

## 3. DRY — 書く前に、既存の置き場所を探す

同じ知識は 1 か所にだけ置く。次のものは**決まった置き場所がある**ので、自分で書き直さない。

| 知識 | 置き場所 |
|---|---|
| 数値パラメータの範囲・基準値・書式・説明 | `ParameterCatalog.all` |
| 数値でない設定項目(比べ方・写し方・説明) | `SettingsFields.others` |
| 設定ファイルを寛容に読む | `KeyedDecodingContainer.tolerant(_:default:)` |
| 小数の丸め | `Double.rounded(toPlaces:)` |
| 写真 ID の並びの正規化と重複除き | `RawgenzoTools.uniqueIDs` |
| 保存と取り消しの登録 | `RawgenzoTools.commit` |
| アプリで開いている写真と違うときの知らせ | `RawgenzoTools.warned` |
| adjust の changes・deltas の形 | `RawgenzoTools.changesSchema` / `deltasSchema` |
| 保存先のパス | `RawgenzoPaths` |

- 書く前に、`grep` で同じことをしている関数を探す。
- 同じ処理を 2 回書いたら、3 回目の前に関数にまとめる。
- 同じ一覧(項目名・ID の並び)を複数の switch に分けて書かない。表を 1 つ作り、そこから引く。

## 4. KISS

- 読んで一度で分かる書き方を選ぶ。凝った抽象・プロトコルは、具体的な型が 2 つそろうまで作らない。
- 入れ子は 3 段までにする。深くなったら `guard` で早めに抜ける。
- 互いに排他な引数の確かめは、ハンドラの先頭にまとめて書く。

## 5. 拡張性 — 足すときの手順

新しいものを足すときは、決まった手順に沿う。手順に無い場所を触ることになったら、手順か設計を見直す。

- **数値パラメータ**
  1. `DevelopSettings` に足す。
  2. `ParameterCatalog.all` に記述を足す。

  スライダー・CLI・AI の道具は、ParameterCatalog から自動で作られる。
- **数値でない設定項目**
  1. `DevelopSettings` に足し、`init(from:)` で `c.tolerant` を使って読む。
  2. `SettingsFields.others` に 1 行足す。

  これで取り消しとハイライトの対象になる。
- **AI の道具**
  1. 群に合う `RawgenzoSurface/*Tools.swift` に `register…` を足す。合う群が無ければ新しいファイルを作る。
  2. `RawgenzoTools.register` の並びに加える。並びの順が tools/list の順になる。
  3. `RawgenzoTools.instructions` に、いつ使うかを 1 行足す。
- **rawdev のコマンド**
  1. `run…()` 関数を足す。
  2. `switch command` に 1 行足す。
  3. `usage` を直す。
- **SONY の別の機種**
  1. `SonyProfile.Model` に機種の定義を足す。書くものは次の 4 つ。
     - EXIF の機種名
     - 表示名
     - id(サイドカーに保存されるので、決めたら変えない)
     - Core Image での名前(見当でよい)
  2. `SonyProfile.models` に並べる。
  3. `rawdev check` で、Core Image がその機種を読めるか確かめる。
     名前が一覧に無ければ、Sony の機種がすべて表示される。その中に機種があれば Core Image での名前を直し、無ければ Core Image では読めない。

  デコーダ・レンズ補正・フォーカス位置の読み方は、SONY の機種で共通。
- **SONY 以外のメーカー**
  1. `Camera/<メーカー>/` に `CameraProfile` に準拠した型を作り、`CameraRegistry.makeDefault()` に足す。
  2. メーカー独自の欄(レンズ補正値・フォーカス位置など)を読むコードは、そのフォルダの中に置く。`CameraProfile` の `lensCorrection`・`focusPoint` から返す。
  3. `RAWMetadata`・レンズ補正・処理段など、共通の部品にメーカーの名前で分岐を書かない。
  4. Core Image が読めない機種は、`RAWSource` を実装した別のデコーダを `makeSource` から返す。

  決めてから足すこと: RAW に補正値が無く、Core Image が補正できる機種でどちらを使うか。いまはデコーダ側の補正を常に切っている(`CoreImageRAWSource.render`)。
- **ルック・構図ガイド・処理段**: CLAUDE.md の「拡張のしかた」に従う。

## 6. 単一責任

- 1 つの型は、1 つの理由でしか変わらないようにする。
  - 道具の登録と、結果の整形は、別の関数にする。
  - 計算と、UI の状態は、別の場所に置く。
- 計算(色・幾何・統計)は RAWCore に置き、UI や道具からは呼ぶだけにする。
- `EditorModel` には、これ以上仕事を足さない。新しい機能の状態は、別の型か `extension` のファイルに分ける。

## 7. 結合

- アプリと道具は、`LiveEditing`(`liveSettings`・`applyLive`・`viewState`)の口だけでつながる。
- グローバルな可変状態を作らない。共有するものは、引数で渡すか、決まった型(`RawgenzoWorkspace` など)に持たせる。

## 8. テスト

- 新しい機能には RAWCore 側のテストを付ける。見た目で確かめにくいもの(幾何・色・文字列)ほど、数値で確かめる。
- 計算は純粋な関数にして、UI なしで試せる形にする。
- 報告の前に、ビルドとテストを通して終了コードを確かめる。実サンプルが要るときは `RAW_SAMPLE_DIR=RAWsample swift test` を使う。
- AI に見せるもの(道具の名前・説明・入力の形)を変えるつもりのない変更では、変更の前後で MCP の tools/list の出力を比べる。差が無いことを確かめる。

## 9. 可読性

- 名前は役割で付ける。略語は、広く通じるもの(ID・URL・RGB など)に限る。
- コメントには「なぜ」を書く。過去に起きた不具合が理由なら、日付と起きたことを添える(例: `2026-10-16 の試験`)。
  「何を」はコードで分かるように書く。
- コメント・UI の文言・エラーの文・コミットメッセージは日本語で書く。
- 周りのコードの書き方(名前の付け方・コメントの量・言い回し)に合わせる。

## 10. エラー処理と堅牢性

- **設定ファイルは寛容に読む。** 項目が欠けている・形が違う・列挙型に未知の値がある、のどれでも、その項目だけ既定値にして読み続ける。
  入れ子の型も含めて、`init(from:)` を手書きし、`c.tolerant` を使う。
  合成された Codable は、項目が 1 つ欠けるだけで全体が読めなくなる。
- **途中で半分だけ変わる、を作らない。** 複数の写真を変える道具は、全部の写真で確かめと計画を済ませてから保存する。
- **黙って捨てない。** 飛ばしたもの・丸めたもの・変えなかったものは、結果の `notes` で知らせる。
- **道具のエラーの文**には、何が悪いかと、どうすればよいかを書く。例: 「…を指定してください」「…を使ってください」
- **`!` での強制アンラップは使わない。** 例外は次の 2 つだけ。
  - 道具の引数のうち、スキーマで必須・型を検証済みのもの(`Surface` がハンドラの前に検証する)
  - 定数で、失敗しないことが明らかなもの

## 書き終えたら確かめること

- [ ] 依存の向きを破っていない
- [ ] 共通の部品に、メーカー・機種の名前で分岐を書いていない
- [ ] 400 行を超えたファイル・40 行を超えた関数が無い。あれば理由をコメントに書いた
- [ ] 3 の表にある知識を、自分で書き直していない
- [ ] 足したものが、5 の手順のとおりに入っている
- [ ] 新しい設定項目を `c.tolerant` で読み、欠けた JSON を読むテストがある
- [ ] 失敗・飛ばし・丸めを、黙って捨てていない
- [ ] ビルドとテストが通り、終了コードを確かめた
- [ ] 道具の見た目を変える気が無いなら、tools/list の出力が変わっていない
- [ ] README・docs・CLAUDE.md のうち、変更に関係するところを直した

## 直すときの進め方(動きを変えない書き換え)

- 動きを変える直しと、変えない書き換えは、別のコミットにする。
- 書き換えは 1 段ずつ進める。1 段ごとに次の 2 つを確かめてからコミットする。
  - ビルドとテストが通る
  - tools/list の出力が変わらない
- 失敗したら、その段を戻してやり直す。上から継ぎはぎで直さない。
