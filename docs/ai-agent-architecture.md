# AI に操作を委譲するアーキテクチャの検討

2026-10-09 時点の検討メモ。まだ何も実装していない。決めてもらいたい点は最後の「相談したいこと」にまとめた。

> 2026-10-16 に実装して main に取り込んだ。実装したもののプロセスと通信は [ai-mcp-architecture.md](ai-mcp-architecture.md) を参照。
> このメモは検討の段階のもので、実装とは違うところがある(例: 外部の AI から MCP で操作する形を先に作り、アプリへの AI の内蔵は未着手)。

## 1. 問いの整理

「GUI を持つソフトの操作を AI に任せる」には、AI がソフトに触る経路が 3 段階ある。

| 段階 | AI が見るもの / 触るもの | ソフト側の協力 | 長所 | 短所 |
|---|---|---|---|---|
| A. 画面操作(computer use) | スクリーンショット / マウス・キー | 不要 | どのソフトでも動く | 遅い・高い・座標ずれで失敗する。画面に出ない意味(下記)が分からない |
| B. アクセシビリティツリー | ボタン・スライダーの名前と値 | ほぼ不要(SwiftUI が自動で出す) | macOS のどのアプリでも一応使える | 「露出 +0.30」は分かっても範囲・単位・副作用・前提が分からない |
| C. 意味の層(セマンティック API) | 「写真」「現像設定」「書き出し」という領域の言葉 | 必要 | 速い・正確・安い・権限を絞れる・取り消せる | ソフトごとに作り込みが要る |

A と B はすでに汎用に存在する(Claude の computer use、macOS の AX API)。**挑戦すべき一般化は C を「どのソフトでも同じ形で作れる」ようにすること**だと考える。
つまり「AI 対応ソフト」とは、GUI と並ぶもう一つの利用者として AI を迎えるための、決まった形の窓口を持つソフトである。

C でなければならない理由が、このプロジェクト自身にある。CLAUDE.md の「はまりどころ」は、画面を見ているだけでは分からない事実の一覧になっている:

- シャープネスは等倍で描くときだけ効く。画面に合わせた表示ではスライダーを動かしても絵が変わらない
  → 画面操作の AI は「効かないので最大まで上げる」と判断しかねない
- 輝度ノイズ除去は 1 を超えると効き方が逆になる
- 傾きを変えると枠が縮む。広げるのは別のボタン
- レンズ補正の「未指定」は「カメラ設定に従う」の意味(nil と off の違い)

人間には注記やツールチップで伝えているこれらを、**機械が読める形で操作の定義に付けておく**ことが、A/B に対する C の本質的な優位になる。

## 2. 全体像

```
            ┌──────────── 利用者(アダプタ) ────────────┐
            │ GUI(SwiftUI)  CLI(rawdev)  MCP サーバー  │
            │ アプリ内エージェント  App Intents(将来)    │
            └───────────────┬───────────────────────────┘
                            │ 同じ「操作面」を呼ぶ
            ┌───────────────▼───────────────────────────┐
  汎用部分  │ Operation Surface(新規・アプリ非依存)       │
            │  ・カタログ: 実体(Entity)・操作(Action)・    │
            │    観測(Observation)を JSON Schema で自己記述 │
            │  ・実行: 検証 → 権限判定 → 取引(取り消し可)    │
            │  ・提案モード / 試行(dry-run) / 監査ログ       │
            └───────────────┬───────────────────────────┘
                            │ アプリが「領域」を登録する
            ┌───────────────▼───────────────────────────┐
  Rawgenzo  │ RawgenzoDomain                             │
            │  実体: Folder, Photo, DevelopSettings, Look  │
            │  操作: set_adjustments, set_crop, apply_look,│
            │        export, select_photos ...            │
            │  観測: preview 画像, ヒストグラム, 白飛び率,  │
            │        メタデータ                            │
            └───────────────┬───────────────────────────┘
                            ▼
                      RAWCore(現像エンジン。変更は最小)
```

要点は 3 つ。

1. **GUI も操作面の一利用者にする。** 人間のスライダー操作も AI の操作も同じ `Action` を通るので、
   取り消し履歴・保存・描画が一本化され、「AI 用の裏口」が仕様からずれていくことがない
2. **AI の居場所を固定しない。** アプリ内にエージェントを持つ(認証情報を渡す)形と、
   外の AI(Claude Desktop / Claude Code / ChatGPT など)がアプリを道具として使う形(MCP)の両方を、同じ操作面のアダプタとして作る
3. **汎用部分とアプリ固有部分の境界を明確にする。** 汎用部分は別ターゲット(後で別パッケージに切り出せる)にし、
   RAWCore も SwiftUI も import しない。これが「他の GUI ソフトにも同じ進化が起きる」ことへの答えになる

## 3. 汎用部分(Operation Surface)の設計

### 3.1 カタログ ― ソフトの自己記述

AI に渡す道具の一覧(Claude の tools、MCP の tools/list、OpenAI の function)は全部ここから生成する。

```
ParameterDescriptor   id, 表示名, 型, 範囲, 中立値, 単位, 表示倍率(UI の ×100 など),
                      説明(「等倍描画でのみ効く」等の注意), nil の意味
ActionDescriptor      id, 説明, 入力スキーマ, 影響(読む/可逆に変える/ファイルを書く/消す),
                      対象(1 枚 / 選択中 / 条件指定), 取り消せるか
EntityDescriptor      id, 属性, 問い合わせできる項目(ISO・レンズ・日付…)
ObservationDescriptor id, 返すもの(JSON / 画像), おおよその費用(画像はトークンが高い)
```

今の Rawgenzo では範囲が UI とコアに分散している(露出の −3...3 や色温度の 2000...12000 は `InspectorView` に直書き、
シャープネスなどは `DetailRanges`、コントラストは `ContrastCurve.range`)。
**`ParameterDescriptor` に集めて、インスペクタのスライダーも AI の道具定義も同じ記述から作る**のが最初の作業になる。
これは AI と無関係にも価値がある(CLI の範囲チェックも同じ記述から作れる)。

### 3.2 実行 ― 取引・取り消し・権限

- **取引(Transaction)**: 1 回の指示で行った変更をまとめて 1 単位にし、まとめて取り消せる。
  今のアプリには取り消し(⌘Z)が無いので、ここで導入する(人間にも効く)
- **影響の段階と権限**:

  | 段階 | 例 | 既定の扱い |
  |---|---|---|
  | 読む | 一覧・メタデータ・プレビュー | 許可 |
  | 提案 | 「この設定にしたらどうか」 | 許可(適用はしない) |
  | 可逆に変える | 現像設定の変更(サイドカー) | 許可。取り消せる |
  | ファイルを書く | 書き出し | 確認する(件数・保存先を見せる) |
  | 消す | (Rawgenzo には無い) | 用意しない |

  Rawgenzo は非破壊編集(元の RAW を書き換えず、設定はサイドカーの JSON)なので、
  「AI が間違えても元に戻せる」が最初から成り立つ。題材として都合がよい
- **提案モード**: AI の変更を確定させず「候補」として持ち、プレビューで前後比較 → 人が採否を決める。
  大量処理では「10 枚だけ試して見せる → 承認 → 残りを適用」の段取りを操作面の機能として持つ
- **監査ログ**: 誰が(人 / どのエージェント)、何を、なぜ(AI の説明文)変えたか。取り消しの単位と一致させる
- **予算**: トークン・画像枚数・金額の上限。超えたら止めて人に聞く

### 3.3 観測 ― AI に何を見せるか

写真の現像は知覚の作業なので、AI に絵を見せないと判断できない。ただし画像は高いので段階を付ける。

1. **数値の観測(安い)**: ヒストグラム、白飛び・黒つぶれの割合、平均輝度、色かぶりの推定、メタデータ。
   「露出を揃える」「白飛びを 0.5% 以下に」はこれだけで回せる。大量処理の主力
2. **縮小画像(中)**: 長辺 1024 程度の JPEG。構図・雰囲気・ルックの判断に使う
3. **前後比較・部分拡大(高)**: 必要なときだけ

「AI に見せる絵」と「人に見せる絵」を同じパイプラインで描くことが大事(シャープネスのように
縮小描画で効かない処理があるため、観測の記述に「この観測で見える処理 / 見えない処理」を書いておく)。
費用を抑える工夫は 8 章にまとめた。

### 3.4 状態の同期 ― 人と AI が同時に触る

- アプリの画面に AI の操作がその場で反映されること(「AI が操作中」の表示、変わったスライダーの強調)
- 人が触ったら AI の取引を中断できること
- **外部の AI が `rawdev` 経由でサイドカーを書き、同時にアプリが開いていると上書きし合う**(アプリはファイル監視をしていない)。
  対策として、アプリが起動中なら外部からの操作はアプリを経由させる(ローカルのソケットで橋渡し)、
  起動していなければ CLI が直接サイドカーを扱う、という二段にする

## 4. AI の居場所: 2 つの形

### 4.1 外部の AI がアプリを道具として使う(MCP)

```
Claude Desktop / Claude Code / 他の MCP クライアント
   └─ stdio ─ rawdev mcp ─(アプリ起動中なら Unix ソケットで橋渡し)─ Rawgenzo.app
```

- **Rawgenzo は認証情報を持たない。** 利用者は自分が契約している AI をそのまま使う
- MCP はソフトに依存しない共通の約束なので、「どの GUI ソフトでも同じ」に最も近い
- ここ(Claude Code)からすぐ試せるので、開発中の検証が回しやすい
- MCP は JSON-RPC なので Foundation だけで書ける(外部依存なしの方針を守れる)。公式の Swift SDK もあるが依存の追加になる

**通信の向き(ルーターに穴を開ける必要はない)**: stdio の MCP は、Mac 上の MCP クライアント(Claude Desktop / Claude Code)が
`rawdev mcp` を子プロセスとして起動し、標準入出力でやり取りする。クラウドの AI が Mac に接続してくるのではなく、
クライアントが AI の API へ外向きの HTTPS で問い合わせ、返ってきた「この道具をこの引数で呼べ」を Mac の中で実行する。
`rawdev mcp` とアプリの橋渡しも Unix ドメインソケットで、ネットワークには出ない。4.2 の内蔵エージェントも外向きの HTTPS だけ。

```
[Mac の中]  Claude Desktop ─stdio─ rawdev mcp ─Unixソケット─ Rawgenzo.app
                 │
                 └─ 外向き HTTPS ─→ AI の API(クラウド)     ← 内向きの接続は一つもない
```

例外は、クラウド側から呼びに来る「リモート MCP」(claude.ai の Web 版のカスタムコネクタなど。ChatGPT も同様の方式と思われるが未確認)。
こちらはインターネットから届く HTTPS の URL が要るので、ポート開放かトンネル(Cloudflare Tunnel など)が必要になり、
写真フォルダを操作できる口を外に公開することになる。**Rawgenzo では採らない**(要るなら認証付きで別途検討)。

### 4.2 アプリが AI を内蔵する(認証情報を渡す)

```
Rawgenzo.app
  └ エージェントパネル(指示欄・計画の承認・作業ログ)
      └ AgentLoop(汎用。tool use の往復・予算・中断)
          └ Provider アダプタ: Anthropic Messages API / OpenAI(Responses API の function calling)
```

- 認証情報は **API キー**。Claude.ai や ChatGPT の月額契約は API の認証情報ではなく、第三者のアプリから使えるものではない
  (OAuth で契約を使わせる仕組みが各社の規約上許されるかは未確認。許されると確認できるまで前提にしない)
- キーは Keychain に置く。`config.json` には書かない(平文で Dropbox に同期されうるため)
- Swift には Anthropic の公式 SDK が無いので、URLSession で HTTP を直接呼ぶ(依存は増えない)
- 道具の定義は 3.1 のカタログから各社の形式に変換する。各社の差は「道具の書式」「画像の渡し方」「停止理由」程度に閉じ込める
- Claude を使う場合の要点(2026-10 時点の API で確認):
  - 既定のモデルは `claude-opus-5-5`。大量の写真の分類のような単純で数の多い仕事は `claude-haiku-5-5` に回す、
    という使い分けはオーナーに選んでもらう(費用に直結するため勝手に決めない)
  - 道具の入力は `strict: true` でスキーマどおりに出させる。`tool_choice` で道具を強制する指定は現行モデルでは使えない
  - 道具一覧とシステムプロンプトは毎回同じ並びにしてプロンプトキャッシュを効かせる(写真ごとの情報は後ろに置く)
  - 急がない大量処理は Message Batches API(料金半額、非同期)が使える
  - 安全側の判定で断られる(`stop_reason: "refusal"`)場合の扱いを UI に用意する

### 4.3 どちらを先にするか

**MCP を先、内蔵を後**を勧める。

- 操作面(3 章)の良し悪しは MCP だけで検証できる。内蔵エージェントは同じ操作面に乗る UI と HTTP の層にすぎない
- MCP は認証情報・課金・キーの保管という難所を後回しにできる
- 「GUI ソフト一般の未来」としても、各ソフトが AI を内蔵するより、ソフトは道具を出し AI は外にいる形のほうが
  一般化しやすいと考える。ただし AI を持っていない利用者にも使えるのは内蔵のほうなので、両方必要という判断は変わらない

## 5. Rawgenzo での具体例(操作面の中身の案)

| 種類 | 名前(案) | 内容 |
|---|---|---|
| 実体 | `folder.list` | 開いているフォルダの写真と主要メタデータ(ISO・レンズ・焦点距離・日時・露出) |
| 観測 | `photo.state` | 現像設定と、各パラメータの範囲・初期値・今の値 |
| 観測 | `photo.stats` | ヒストグラム・白飛び率・黒つぶれ率・平均輝度 |
| 観測 | `photo.preview` | 長辺を指定した JPEG(既定 1024) |
| 操作 | `photo.adjust` | 露出・WB・コントラスト・HDR・色・ディテールの一部変更(差分で渡す) |
| 操作 | `photo.crop` | 比率・傾き・位置。枠を収める規則(CropFitting)は操作面の内側で守る |
| 操作 | `photo.look` | ルックと強さ |
| 操作 | `photos.apply` | 条件(ISO ≥ 6400 など)か ID の列に、同じ差分を適用 |
| 操作 | `photos.copy_settings` | 1 枚の設定を他へ写す(項目を選べる) |
| 操作 | `photos.select` | アプリの選択状態を変える(「選び出し」の結果を人に見せる) |
| 操作 | `export` | 書き出し(確認が要る段階) |

想定する指示の例と、それに要る機能:

- 「ISO 6400 以上は輝度ノイズ除去を 0.5 に」 → メタデータでの条件指定 + 一括適用(画像を見なくてよい)
- 「この 1 枚の色を基準に、同じ場面の写真の WB と露出を揃えて」 → 数値の観測 + 縮小画像
- 「水平を直して 3:2 で」 → 縮小画像を見て角度を推定 + 枠の規則
- 「夕景だけ選んで」「ピントの甘いものを外して」 → 画像の分類。費用が大きいので、まずメタデータで絞り、
  埋め込みサムネイルで判定する段取りにする

**今のアプリに無くて、先に要るもの**(AI と関係なく人にも役立つ):

- 取り消し(⌘Z)
- 複数選択と一括適用(CLI はフォルダ単位でできるが、アプリにはない)
- 選び出しの結果を残す場所(レーティング・ラベル)。サイドカーの保存形式を変えることになるので要相談

## 6. 段階的な進め方(案)

| 段階 | 内容 | 確かめ方 |
|---|---|---|
| 0 | `ParameterDescriptor` に範囲・説明を集約し、インスペクタと CLI をそこから作る | 既存テスト + 記述と UI の範囲が一致するテスト |
| 1 | 操作面の核(カタログ・取引・取り消し・権限・監査ログ)を RAWCore 非依存のターゲットとして作る。GUI の変更も取引を通す | 単体テスト。⌘Z が効くことをオーナーに確認してもらう |
| 2 | 観測(統計・縮小画像)と `rawdev` の JSON 入出力 | 実サンプルでの数値テスト |
| 3 | `rawdev mcp`(stdio)。Claude Code から実際に操作してみる | ここで操作面の設計を評価し、直す |
| 4 | アプリ起動中の橋渡し(ソケット)と「AI が操作中」の表示 | オーナーの目視 |
| 5 | アプリ内エージェント(Anthropic / OpenAI アダプタ、Keychain、承認 UI、予算) | オーナーの API キーで試す(費用が掛かるので事前に了承をもらう) |
| 6 | 汎用部分を別パッケージに切り出し、他のアプリにも使える形か検証(App Intents アダプタもここで検討) | 小さな別アプリで使ってみる |

段階 0〜3 は Rawgenzo 単体でも価値がある(範囲の一元化・取り消し・JSON での自動化)ので、途中で止めても無駄にならない。

## 7. 正直に書いておくこと

- **確かめていないこと**: AI が縮小画像から色温度や傾きをどこまで正確に判断できるか(試してみないと分からない)。
  OpenAI 側の API の細部は今回確認していない。Apple の App Intents が外部 AI にどう公開されるかの最新状況も未確認
- **AI に向かない部分**: 色の好みは主観で、AI の「良い」はオーナーの「良い」と一致しない。
  主戦場は「定型・大量・条件で選ぶ」作業で、作品としての仕上げは人が持つ、という前提で設計している
- **汎用化の限界**: 操作面の形(カタログ・取引・観測・権限)は汎用にできるが、何を実体・操作とするかの設計は
  ソフトごとに人が考える必要がある。そこを自動化するなら、アクセシビリティツリーから操作面の下書きを作る道具が考えられるが、
  意味(1 章の「はまりどころ」)までは自動では得られない

## 8. 画像を流し込み続けないための工夫

人間の現像は「スライダーを少し動かす → 画面を見る → また動かす」の繰り返しである。これを AI にそのまま真似させ、
毎回画面全体のキャプチャを送ると、次の 3 つが重なって費用が膨らむ。

1. **1 枚が無駄に高い**: 画面全体には写真以外(パネル・文字・余白)が多く、それらは JSON で送れば数十トークンで済む情報。
   しかも画像は送る前に縮小されるので、大きな画面を送っても写真に割ける解像度は下がる
2. **履歴に溜まる**: 往復のたびに過去の画像も毎回送り直すので、1 枚の写真で n 回動かすと画像の費用は n² に比例して増える
3. **枚数に比例する**: 300 枚のフォルダなら、それがさらに 300 倍になる

**概算**(画像のトークン数は従来の目安「幅 × 高さ ÷ 750」で計算。現行モデルの値は count_tokens で確かめてから決める):
画面キャプチャ 1 枚 約 2,000 トークン、1 枚の写真に 20 往復、過去の画像を全部送り直すと
2,000 × (1 + 2 + … + 20) ≈ 42 万トークン。300 枚で約 1.3 億トークン、`claude-opus-5-5`(入力 $4 / 100 万)で約 $500。
人の操作を真似る限り、この形はどう工夫しても高い。

以下、効果の大きい順に工夫を挙げる。

### 8.1 ループを AI の外に出す(目標値で指示する)

人がスライダーを往復させるのは、目で見て確かめる以外に手段がないから。AI は数値で目標を言えるので、
**「露出を +0.1 にして見せて」ではなく「平均輝度を 0.45 に、白飛びを 0.5% 以下に」と目標で指示し、
目標に合う値の探索(二分探索など)はアプリが手元で行う**。AI との往復は 1 回で済み、画像も不要になる。

操作面には通常の `photo.adjust`(値を設定)に加えて、目標を受け取る操作を用意する:

| 操作(案) | 目標の例 | アプリ側の探索 |
|---|---|---|
| `photo.solve_exposure` | 平均輝度・白飛び率・黒つぶれ率 | 露出・ハイライト回復を探索 |
| `photo.solve_white_balance` | 中立にしたい領域 / 基準写真の色に合わせる | 色温度・色かぶりを探索 |
| `photo.solve_level` | 水平線を水平に | 下記の水平検出の角度を使う |
| `photos.match` | 基準写真の統計(輝度分布・色)に揃える | 1 枚ずつ探索 |

これは他の GUI ソフトにも一般化できる考え方である。人間向けの UI は「直接操作 + 目で確認」に最適化されているが、
AI 向けの操作面は「宣言的な目標 + アプリが解く」にするべきで、両者は同じ操作の粒度でなくてよい。

### 8.2 画像の代わりに数値と端末内の認識を渡す

多くの判断は画像を見なくても、手元で計算した数値で足りる。

- **統計**: ヒストグラム(32 区間)、白飛び・黒つぶれ率、写真を 8×8 に区切った各区画の平均の明るさと色
  (192 個の数値で数百トークン。構図の明暗の配置まで分かる)
- **macOS の Vision フレームワーク(端末内で動き、費用が掛からない)**:
  水平線の角度の検出、シーンの分類(夕景・室内など)、注目領域(サリエンシー)、顔の検出、
  画像の特徴量(似た写真のまとまりを作れる)、美的評価のスコア。
  ピントの甘さはラプラシアンの分散のような古典的な指標で手元で測れる
  - 「夕景だけ選ぶ」「ピンぼけを外す」「水平を直す」は、ここだけでかなりの部分ができる見込み。
    ただし Vision の各機能が要件の macOS 13 で使えるか(美的評価は新しい macOS が要るはず)、
    α7S III の写真で精度が足りるかは未確認

AI には「数値で判断できないものだけ画像を見る」という方針をシステムプロンプトと道具の説明で伝える。

### 8.3 画像を送るときは安く・密に

- **画面ではなく写真だけ**を送る。長辺 512〜1024 で足りることが多い
- **目的に合わせた切り出し**: ノイズやシャープネスは縮小画像では見えないので、等倍で 256×256 程度の部分だけ切り出す
- **一覧で 1 枚にまとめる**: 露出 −1/0/+1 の 3 案、ルック 6 種類などをアプリが並べて描き、ラベルを付けて 1 枚の画像にする。
  「どれが良いか」を 1 往復で決められ、往復回数が減る(写真の段階露出と同じ発想)
- **前後比較を 1 枚に**: 左右に並べて送る
- **見るべきものを強調した画像**: 白飛び部分を赤く塗った画像、輝度だけの画像など。低解像度でも判断しやすい

### 8.4 履歴を太らせない

- 画像は既定では返さず、**AI が必要なときに観測の道具で取りに来る**(取りに来る形。道具の説明に「高い」と書く)
- 変更後は差分の数値だけを返す(「平均輝度 0.38 → 0.45、白飛び 0.2%」)
- 古い画像の結果は API の機能(Claude ではコンテキスト編集の `clear_tool_uses`)で消す。
  会話の履歴を自前で書き換えるのは避ける(現行モデルは書き換えた履歴を拒むことがあり、キャッシュも効かなくなる)
- **写真 1 枚ごとに新しい短い会話にする**: 全体を指揮するエージェントは文字の要約だけを持ち、
  1 枚の調整は使い捨ての会話(サブエージェント)で行う。画像は使い捨ての側にしか入らない
- 基準写真のように何度も見せる画像は、会話の先頭に置いてプロンプトキャッシュに乗せる(キャッシュの読み込みは通常の 1/10 程度の料金)

### 8.5 「少数で決めて、多数にはアプリが当てる」

300 枚に AI を 300 回使うのではなく:

1. アプリが撮影時刻の間隔と Vision の特徴量で写真を場面ごとにまとめる(費用ゼロ)
2. 場面ごとに代表の 1〜2 枚だけ AI が見て、**手順(レシピ)**を決める。例:「この場面は平均輝度 0.42、WB は 5200K、ルック film 0.6」
3. 残りの写真には、アプリがレシピを目標値として 8.1 の探索で当てる(費用ゼロ)
4. 結果を一覧(コンタクトシート)にして AI か人が 1 枚で確認し、外れだけ直す

AI の費用が写真の枚数ではなく場面の数に比例するようになる。急がない処理は Message Batches API(料金半額)で回せる。
単純な分類だけを安いモデル(`claude-haiku-5-5` など)に回す使い分けもできる(どのモデルを使うかはオーナーが決める)。

### 8.6 概算の比較(同じ 300 枚・10 場面の場合の見込み)

| やり方 | AI に送る画像 | 概算の入力トークン |
|---|---|---|
| 画面キャプチャで人の操作を真似る(20 往復、履歴に残す) | 6,000 枚(履歴込みで延べ 6 万枚超) | 約 1.3 億 |
| 写真だけ・目標値の操作・1 枚ごとに使い捨て(1 枚あたり画像 2 枚) | 600 枚 | 数十万〜100 万 |
| 場面ごとのレシピ + コンタクトシートで確認 | 30 枚程度 | 数万〜10 万 |

数字は桁を見るための見込みで、測っていない。段階 2〜3 で実際に測る。

### 8.7 汎用アーキテクチャへの反映

この章の工夫は Rawgenzo 固有ではなく、操作面(3 章)の決まりとして一般化できる:

- 観測には**費用と忠実度**を記述し、AI が選んで取りに来る(画像を押し付けない)
- 観測は**数値・構造(安い)→ 端末内の認識 → 部分画像 → 全体画像(高い)**の段に分ける
- 操作には**値の設定**と**目標の宣言(アプリが解く)**の 2 種類を用意する
- 大量処理は**代表で決めてアプリが展開する**段取りを操作面の機能として持つ

## 9. 相談したいこと

1. AI の居場所: MCP を先にし内蔵を後にする順序でよいか
2. 汎用部分の置き場: 同じリポジトリの別ターゲットで始め、後で切り出す形でよいか(名前も含めて)
3. 依存: MCP と HTTP を Foundation で自作する(依存なしを維持)か、公式 MCP Swift SDK を入れるか
4. 保存形式: レーティング・ラベル・AI の提案履歴をサイドカーに足すか(schemaVersion を上げる)
5. 対象: 最初に試す指示を 2〜3 個決めたい(例:「ISO で一括ノイズ除去」「基準写真に WB と露出を揃える」「水平補正 + 3:2」)
6. 作業はブランチで進める(UI と保存形式に関わるため)
7. 8.1 の「目標値で指示する操作」と 8.2 の Vision による認識は AI 抜きでも「自動補正」として使える。
   先にこれを人向けの機能(自動露出・自動水平など)として作るか
